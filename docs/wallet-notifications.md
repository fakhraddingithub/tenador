# اعلان تراکنش‌های کیف پول

تمام واریزها و برداشت‌های جدیدِ مسیرهای فعلی کیف پول به یک سازوکار متصل‌اند: پاداش نظر، کردیت دستی/خودکار مربی، افزایش/کاهش موجودی توسط ادمین، پرداخت سفارش، برگشت مبلغ سفارش، تبدیل موجودی به کد تخفیف، برگشت باقیمانده کد و بازگشت کردیت مربی هنگام لغو سفارش.

## ثبت و ارسال

هوک مشترک سه مدل `WalletTransaction`، `ReviewCreditTransaction` و `CoachWalletTransaction`، هنگام ایجاد رکورد جدید در تراکنش MongoDB، اعلان تکی `UserNotification` و رسید ارسال `WalletNotification` را در همان session می‌سازد. به همین دلیل rollback پول، اعلان و رسید را هم حذف می‌کند. ذخیره مجدد رکورد قبلی یا واردکردن تاریخچه قدیمی بدون تراکنش مالی، اعلان جدید نمی‌سازد.

اعلان سایت فقط برای صاحب کیف پول ثبت می‌شود و مبلغ، جهت و توضیح تراکنش را دارد. ایمیل نیز همین اطلاعات و لینک کیف پول را نمایش می‌دهد؛ متن توضیح در HTML escape می‌شود.

در درخواست‌های Next.js، `after()` ارسال ایمیل و Web Push را پس از پایان پاسخ اجرا می‌کند. تابع سازگارِ پاداش نظر هم به همین رسید مراجعه می‌کند و دیگر اعلان جداگانه‌ای ایجاد نمی‌کند. شناسه رسید از منبع و شناسه دفتر تراکنش ساخته می‌شود؛ ارسال‌کننده با قفل اتمی پنج‌دقیقه‌ای از اجرای هم‌زمان روی یک رسید جلوگیری می‌کند.

موفقیت ایمیل و Push جداگانه ثبت می‌شود. خطای SMTP یا نبود تنظیمات ایمیل، رسید را برای تلاش مجدد نگه می‌دارد و موجودی را تغییر نمی‌دهد. کاربر فاقد آدرس ایمیل، اعلان سایت و Push را دریافت می‌کند و وضعیت «بدون ایمیل» در رسید ثبت می‌شود؛ گیرنده جایگزین ساخته نمی‌شود.

## بازیابی خطاها

مسیر `GET /api/cron/wallet-notifications` فقط با `Authorization: Bearer <CRON_SECRET>` اجرا می‌شود. برنامه روزانه ساعت ۰۵:۰۰ UTC به `vercel.json` اضافه شده؛ ارسال عادی منتظر این برنامه نمی‌ماند. روی میزبانی دیگر باید همین مسیر توسط زمان‌بند امن فراخوانی شود. متغیرهای SMTP موجود و `CRON_SECRET` باید در محیط استقرار تنظیم باشند.

هر اجرا حداکثر ۱۰۰ رسید سررسیدشده را با هم‌زمانی پنج بررسی می‌کند و پس از ۳۰ ثانیه دسته جدید شروع نمی‌کند. رسیدهای باقیمانده برای اجرای بعد حفظ می‌شوند. قفل اجرای قطع‌شده پس از پنج دقیقه قابل بازیابی است. حذف سفارش یا دفتر تراکنش نباید رسیدهای ارسال را حذف کند.

اعلان سایت به‌واسطه ثبت اتمی و شناسه ثابت تکرار نمی‌شود. در ایمیل، ثبت موفقیت و شناسه ثابت `Message-ID` تکرارهای معمول را کنترل می‌کند؛ SMTP تضمین سراسری «دقیقاً یک بار» ندارد و قطع فرایند پس از پذیرش ایمیل ولی پیش از ذخیره نتیجه می‌تواند در تلاش بعدی ایمیل تکراری بسازد. Push از سرویس موجود با ارسال best-effort استفاده می‌کند.

## بررسی

`npm run test:wallet-notifications` از MongoDB replica set موقت و فرستنده‌های ساختگی استفاده می‌کند و هیچ ایمیل واقعی ارسال نمی‌کند. پوشش شامل سه منبع دفتر، واریز/برداشت، rollback، درخواست تکراری، ارسال هم‌زمان، خرابی SMTP، عدم تکرار کانال موفق، کاربر بدون ایمیل، بازیابی قفل و مجوز مسیر cron است.
