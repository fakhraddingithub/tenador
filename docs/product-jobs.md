# تولید مرحله‌ای محصول

مسیر پیش‌فرض MCP برای درخواست «این لینک را بساز/بازسازی کن»:

`start_product_job → prepare → analyse → write + images → review → [revise → review] → commit`

ChatGPT فقط دسته/محصول را پیدا می‌کند، درخواست را ثبت می‌کند و با `get_product_job` وضعیت را می‌گیرد. مدل میزبان چت مسئول نوشتن JSON یا مدیریت عکس‌ها نیست. `resume_product_job` فقط پاسخ واقعی ادمین را به کار متوقف‌شده اضافه می‌کند. ابزارهای دستی قبلی برای JSON آماده باقی مانده‌اند؛ نباید برای دورزدن رد بازبین استفاده شوند.

## هماهنگی محتوا

- همان `buildProductDraftPrompt` و تنظیمات جاری پنل مبنا هستند؛ متن نگارش جدید در کد جایگزین قواعد پنل نشده است.
- تحلیلگر JSON ساختاری و شواهد دارای نقل‌قول دقیق از منبع را می‌سازد. منبع کامل هم به نویسنده داده می‌شود؛ خلاصهٔ تحلیلگر جای منبع را نمی‌گیرد.
- نویسنده فقط توضیحات کوتاه و کامل را با هم می‌نویسد. قواعد عمومی و قواعد مرتبط از همان مدل ترکیب پرامپت گرفته می‌شوند؛ فهرست برندها/سری‌های نامرتبط برای نویسنده ارسال نمی‌شود.
- بازبین مستقل، محصول مؤثر نهایی را با تمام قواعد پنل مقایسه می‌کند: هویت/نسل/رنگ، مشخصات، متن، مخاطب، امتیازات، عمق تحلیل و منشأ تصاویر. وجود هر ایراد یا check ناموفق جلوی ذخیره را می‌گیرد. حداکثر دو دور اصلاح متن مجاز است.
- ایراد ساختاری/ابهام factual نیازمند اطلاعات ادمین است؛ با حدس یا بازنویسی صرف حل نمی‌شود. کیفیت معنایی همچنان ارزیابی مدل است و تضمین مطلق ندارد.
- بازبینی تصاویر مبتنی بر منشأ لینک و اطلاعات محصول است؛ بررسی بصری مدل انجام نمی‌شود. تصاویر مشکوک باید رد شوند. HTML متن با allowlist پاک‌سازی می‌شود.
- در بازسازی، قیمت پایه، تصاویر، واریانت‌ها و موجودی حفظ می‌شوند. توضیحات با دادهٔ موجود و منبع جدید تطبیق می‌یابند. این مسیر جای تغییر قیمت/موجودی یا جایگزینی تصاویر نیست.

## اجرا و تنظیمات

متغیرها در `.env` قرار دارند:

```dotenv
PRODUCT_AI_PROVIDER=gemini
PRODUCT_AI_MODEL=gemini-2.5-pro
PRODUCT_AI_MAX_TOKENS=16000
PRODUCT_JOBS_BASE_URL=https://tenador.com
PRODUCT_JOBS_WORKER_SECRET=<random-secret-shared-with-web-process>
PRODUCT_JOBS_POLL_INTERVAL_MS=15000
PRODUCT_JOBS_ERROR_INTERVAL_MS=15000
```

کلید مدل از همان `GEMINI_API_KEY` یا `OPENAI_API_KEY` موجود خوانده می‌شود. مدل محصول مستقل از مدل دستیار ادمین است. اشتراک ChatGPT هزینهٔ API را پوشش نمی‌دهد. متغیرهای اتصال ImageKit موجود نیز لازم‌اند. کلید Gemini نباید وارد commit شود. نام مدل از مستندات رسمی قابل بررسی است: https://ai.google.dev/gemini-api/docs/models/gemini-2.5-pro

پس از انتشار کد و اعمال env در سرویس وب، یک پردازش دائمی جدا اجرا کنید:

```bash
npm run worker:products
```

این پردازش سبک است و دیتابیس/مدل را مستقیم بارگذاری نمی‌کند؛ با secret، هر بار یک مرحله را در `POST /api/internal/product-jobs` اجرا می‌کند. به‌این‌ترتیب runtime خود Next، aliasها، ممیزی و invalidation کش یکسان می‌مانند. خود endpoint باید بودجهٔ اجرای ۱۸۰ ثانیه داشته باشد. کلید worker نباید به مرورگر یا MCP برگردد.

### اجرای دائمی روی Vercel

`vercel.json` یک Daemon به نام `product-jobs` با یک نمونه در `iad1` و حافظهٔ `1Gi` تعریف می‌کند. `workers/Dockerfile.products` فقط فایل پردازشگر را در Node 24 کپی می‌کند؛ `.env` و کلیدها داخل image قرار نمی‌گیرند. Cronهای قبلی سایت حفظ شده‌اند.

1. در **Project → Settings → Environment Variables**، متغیرهای `PRODUCT_JOBS_BASE_URL`، `PRODUCT_JOBS_WORKER_SECRET` و دو interval بالا را برای **Production** از `.env` وارد کنید. secret پردازشگر و endpoint وب باید یکسان باشد. پوش `.env` به‌تنهایی متغیرهای runtime کانتینر را تنظیم نمی‌کند.
2. متغیرهای `PRODUCT_AI_*`، کلید API مدل و تنظیمات فعلی دیتابیس/ImageKit نیز باید در سرویس وب قابل دسترس باشند. کلید Gemini فقط در محیط Production تنظیم می‌شود، نه در Git.
3. Root Directory پروژه باید ریشهٔ مخزن باشد. تغییرات `master` را به Production deploy کنید؛ Preview پردازشگر را اجرا نمی‌کند.
4. در **Daemons → product-jobs → Logs** پیام `Product job dispatcher started` را بررسی کنید. پیام `Processed product job stage` نشان می‌دهد یک درخواست مرحله پردازش شده؛ موفقیت نهایی را از `get_product_job` و `completed` بررسی کنید. خطای 401 یعنی secret اشتباه یا حفاظت دسترسی جلوی endpoint را گرفته است.

با SIGTERM درخواست در حال اجرا تا سقف ۱۹۰ ثانیه فرصت تکمیل دارد و انتظار بین درخواست‌ها فوراً قطع می‌شود؛ تنظیم Vercel برای خاموش‌شدن ۲۱۰ ثانیه است. در صف خالی هر ۱۵ ثانیه بررسی انجام می‌شود؛ پس از پردازش مرحله، ادامه سریع‌تر است. اجرای هم‌زمان نسخهٔ لپ‌تاپ دیگر لازم نیست. Daemon حتی در حالت انتظار مصرف حافظه و هزینه/سهمیهٔ میزبان دارد.

مستندات رسمی: https://vercel.com/docs/daemons و https://vercel.com/docs/daemons/config-reference

آزمون کانتینر در محیط توسعه با Docker:

```bash
docker build -f workers/Dockerfile.products -t tenador-product-jobs workers
docker run --rm --env-file .env tenador-product-jobs
```

اجرای فرمان دوم با آدرس production، صف واقعی سایت را پردازش می‌کند؛ برای آزمایش ایزوله آدرس سرور آزمایشی و secret همان سرور را بدهید.

برای توسعه `PRODUCT_JOBS_BASE_URL=http://localhost:3000` قرار دهید و وب و worker را جدا اجرا کنید. سرور آزمایشی را به دیتابیس زنده وصل نکنید. در این تغییر، نه worker تولید اجرا شده و نه محصول زنده ساخته/بازسازی شده است.

## پایداری و محافظت

- صف و checkpoints در `ProductJob` در MongoDB هستند؛ Redis جدید لازم نیست. قطع چت job را لغو نمی‌کند.
- `requestKey` در هر درخواست منطقی ثابت است و با userId شاخص یکتا دارد. ورودی متفاوت با همان کلید رد می‌شود. ساخت کار تازه با کلید تازه یک درخواست تازه محسوب می‌شود.
- lease اتمیک ۱۰ دقیقه‌ای مانع اجرای هم‌زمان یک مرحله می‌شود. خروجی worker قدیمی پس از ازدست‌دادن lease پذیرفته نمی‌شود. بازیابی بعد از crash ممکن است تا انقضای lease زمان ببرد.
- هر مرحله حداکثر سه تلاش فنی دارد؛ retry هزینهٔ مدل را ممکن است افزایش دهد. خروجی موفق نویسنده و هر عکس جداگانه checkpoint می‌شوند. عکس‌ها دو lane موازی با timeout دارند و ترتیب خروجی مطابق انتخاب اولیه حفظ می‌شود.
- محصول و نتیجهٔ completed کار در **همان تراکنش** ذخیره می‌شوند. ID محصول تازه از قبل رزرو می‌شود. قطع ارتباط بعد از commit محصول دوم نمی‌سازد.
- در هر مرحله دسترسی ادمین دوباره خوانده می‌شود. قبل از ثبت، hash پرامپت و نسخهٔ محصول بررسی می‌شود. واریانت‌های تغییرکرده هم کار بازسازی را متوقف می‌کنند.
- job شامل snapshot منبع، پرامپت، مدل، شواهد، خروجی نویسنده و گزارش بازبین است؛ endpoint عمومی این داده‌ها یا کلیدها را افشا نمی‌کند. نگهداری/پاک‌سازی سوابق باید مطابق سیاست سایت انجام شود؛ حذف خودکار فعلاً فعال نیست.
- وضعیت‌های `queued/running` به معنای موفقیت نیستند؛ فقط `completed` و `result.saved` ثبت قطعی را نشان می‌دهند. `needs_input` یعنی سؤال از ادمین؛ `failed` یعنی عدم ثبت. کار failed در مرحله commit خودکار از ابتدا اجرا نمی‌شود.

## آزمون

`npm run test:product-jobs` با replica set موقت MongoDB، مدل‌ها و تراکنش واقعی اجرا می‌شود. فقط شبکه، پاسخ مدل و سرویس تصویر شبیه‌سازی می‌شوند؛ این تست کیفیت ادبی مدل واقعی را اثبات نمی‌کند. آزمون پذیرش production باید روی محصول غیرفعال با منبع مشخص و بررسی انسانی انجام شود.
